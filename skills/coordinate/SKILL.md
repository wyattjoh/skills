# Coordinate

Take the user's ideas, gripes, links and requests for one domain, often half-formed, and see each through, mostly by delegating, so this session stays free for the next item. The domain's **backlog** is your only memory across compaction and restarts. It is a structured document the `coordinate` CLI owns: you record every state change through `backlog`, `item` and `finding` commands and read it back with `coordinate backlog show`, never by editing a file. You are a router, not a pipeline: nothing here merges, lands, pushes or opens a PR unless the user names that integration for the item.

`coordinate` below means the `coordinate` command when `command -v coordinate` finds it, otherwise `bun $SKILL_DIR/scripts/coordinate.ts`. `coordinate start` and `coordinate status --resume` may install a `coordinate` wrapper in `~/.local/bin`; the `coordinate *` allowlist entry is the user's to add. Briefs, the notify line and anything a delegate runs keep the absolute `bun <skill path>/scripts/coordinate.ts`, since a delegate may run another harness or machine. Its `--help` (and each subcommand's) is the manual for flags and output. Exit 0 is done, 1 is a refusal to act on, 2 is a check that could not run: fix what it prints and run it again. Read every call's exit code and output, since a call that never started prints nothing; run `coordinate` from a folder that outlives the work, such as the main checkout, never from inside a worktree you are about to remove. Text views (`backlog show`, `status --resume`) hide closed items: add `--done` whenever closed-item history is relevant. Use the `herdr` skill for any `hc` or `herdr-app` work the script does not cover.

## Start

Run `coordinate start <domain>`. It labels this terminal, creates the backlog document if missing, takes the domain's coordinator lease, and prints status, the sweep report and quiet delegates. It refuses (exit 1) while another coordinator holds a live lease, naming its machine and terminal: go to that one, or start once its lease lapses ([leases](references/backlog.md#coordinator-leases)). When it names a legacy Markdown backlog, that file is reference only: read it for context and record what still matters through the commands below. Then:

- **Boundary**: `coordinate backlog boundary add <path>` for each repo or folder the domain owns, `--adjacent` for the ones it reads but does not own. Only owned paths feed status, watch and sweep. Ask once when either list is unclear. Done when `backlog show` lists both and the user has seen them in two lines.
- Run `coordinate backlog show` and read every open item and finding. Set or refresh the domain's focus line with `coordinate backlog focus --md "<what the domain is doing now>"`; it also renames your tab to `<Domain> · <short focus>` (`<Domain> · No active focus` once cleared), so keep the focus current rather than renaming the tab yourself. `coordinate start` arms the watcher; on `watcher unavailable`, use the [Watch fallback](#watch-fallback).
- Report what finished, what waits on the user as self-contained asks, what runs, and what you take next.

After compaction or a restart, run `coordinate status --resume`. It arms the watcher when none runs; on `watcher unavailable`, use the [Watch fallback](#watch-fallback).

## Each item

A question gets an answer: read what it needs and reply. A change is an item:

1. Restate it in one line and name what it touches. Check its ripple: what depends on it, what it duplicates or contradicts, from the real files (or a subagent's conclusion).
2. Decide or ask (below), then route it: **answer**; **build** here when it fits one turn with no worktree, branch, running app or render to check; otherwise **delegate**.
3. Record what outlives the turn in the same turn (commands in [Backlog](#backlog)): `item add` for anything not finished this turn, then its status, decisions, ask or close.

**Drift test**, before each action: does it change something outside the boundary, or go past the item? Either yes: say "This moves into <X>, outside <domain>" and route it. Adjacent work is a delegated task with the user's yes for that repo. Another domain of the user's gets an item in that domain's backlog: `coordinate item add "<title> (from <domain>)" --domain <other>` (refused until that domain has a backlog, which `coordinate start` or `coordinate spawn` creates). Other people's work stays theirs; raise it only when it blocks the domain.

## Decide or ask

**Decide** what sits inside the scope the user asked for and is reversible: say what you chose and why in one line, and go on. What their instructions, a policy or an item's decisions already approve is a decision too: take the step and cite it.

**Ask** when the answer changes what gets built, spends time or money they would notice, reaches anyone outside, is their taste, or their rules require their yes. A delegate's question is an ask even when you could decide it, unless the brief, their instructions, an existing policy or an item's decisions answer it; then answer and cite that. Search those first: an answer already given is a decision.

Every question to the user is a **backlog ask** on an item, recorded in the turn you raise it, so the Backlog panel (its Waiting On You list shows it and takes its answer), another session and the manager see it. A question with no item gets one first (`item add`). Record it with `coordinate item update <id> --status waiting-user --ask-md "<question>" --context-md "<why it came up>" --option-md "<label> :: <detail>" --rec <label> --why-md "<reason>"`. Repeat `--option-md` for each choice; omit ` :: <detail>` when it has no detail. Labels stay plain: use only the label for `--rec` or when answering with `--answer`. When you need the answer now, in this conversation, also put it to the user in chat or a question tool prompt ([Claude Code](references/harness-claude.md#questions)), mirroring the ask, self-contained: what, why, the options with consequences, and your recommendation.

Record the user's answer, wherever they give it (chat, a question tool), in the turn they give it, so the ask closes everywhere: `item update <id> --answer <label>`, or `--answer-md "<their words>"` for a free-text answer, plus `[--note-md "<note>"]` (it clears the ask and keeps the answer as a decision; the note records accompanying context), then set the next status. If the user asks to discuss instead, record `--answer "Discuss"` or `--answer "Discuss: <note>"`; keep the ask open and the item waiting-user until they give an actual answer.

Batch questions, most consequential first, five at most; the rest wait as backlog asks on their items. A question a delegate is blocked on goes out at once. A dismissed or unanswered question stays open as its backlog ask: absorb what they said, revise the ask, and raise it again. When an answer establishes a reusable rule for later cases, formulate it as a policy and record that with `coordinate backlog policy add --md "<policy>"`.

## Delegate

- One delegate per task, each in its own Herdr space: `coordinate delegate <name> --task "<few words>" --repo <path> --harness pi|claude ...` makes `<repo>/.claude/worktrees/<name>` on `<branch_prefix><name>`. Use `--worktree <path>` to start a fresh session in an existing linked worktree without creating a branch; it refuses a worktree with a live delegate. `--cwd` is for a domain with no repo; `--no-space` puts it in a tab of your space. Invoking this skill is the user's request for these sessions and spaces.
- A repo declares how to prepare a fresh worktree in a committed `.claude/coordinate.json`: `{"worktreeSetup": ["bun install --frozen-lockfile", ...]}`. A `--repo` launch (local or remote) runs each command in order in the new worktree, ten minutes each, before the harness starts, logging to its `.scratch/setup.log`. A malformed declaration or a command that fails or times out refuses the launch (exit 1) and keeps the worktree and branch, with no harness started: read the log, fix the cause, then remove the worktree and branch (`git worktree remove`, `git branch -D`, after checking it holds nothing) before launching again under the same name.
- Brief it from [brief.md](references/brief.md) (`--brief`). Whenever the user names a skill for the delegate (`pr-review`, `retro`, an implement skill), pass it as `--skill <name>` with its arguments in `--args`, never as text in the brief: a user-invoked skill reaches the delegate only as its first message, so a brief cannot start it. `--skill` takes any skill installed for the harness, and the harness reports a missing one. To implement a spec or ticket, pass `--skill implement-spec` for a spec, `--skill implement` for a single ticket, with `--args "<ref>. <rest>"`. For a Tasks MCP UUID, look it up in the Tasks MCP to tell a Spec from a Task, and make `<ref>` `<UUID> via Tasks MCP`; for a file, `<ref>` is its path. `<rest>` is the user's request condensed, plus the item's decisions and the policies that bind the delegate. Pass `--brief` alongside it with Boundary, Stop points and Report filled; the first message then tells the delegate to follow those sections.
- Harness and model: pass `--harness pi|claude` unless the effective policy has an enabled default. Omit `--model` by default, and say the choice in one line. Read [harness-policy.md](references/harness-policy.md) before passing a model, editing policy, or when a launch or resume is refused on policy grounds.
- Pass `--item <id>`: it is required from your terminal, and `coordinate delegate` records the delegate (name, session, branch, worktree, brief and report) on that item and sets it to delegated. A delegate starting a child review passes no `--item`. Done when the delegate shows a status and `backlog show` lists it under the item.
- Each machine has a delegate budget, by default `max(2, floor(cores / 4))`, set with `max_fleet_delegates` (and `max_fleet_delegates_by_machine`). `--over-budget` overrides only the capacity refusal, never harness policy. When an authorized launch hits the cap and should wait, run the same command again with `--queue-if-full`. On a capacity wake or a `capacity-unavailable` event, read [capacity.md](references/capacity.md) before retrying.
- To run a delegate on another Herdr machine, add `--machine <name>` to a `--repo` launch; the repo needs a checkout recorded with `coordinate backlog boundary add <repo> --machine <m> --checkout <path>`. Before launching, verifying or ending one, or on a `machine-unreachable`, `notify` or `delegate-outbox-invalid` event, read [remote.md](references/remote.md). Its REPORT.md is read from the parked copy here first. `--worktree` is local-only.
- Run the heavy gates the brief names as "coordinator runs at landing" once before landing.
- A delegate records what it notices outside its task with `coordinate finding add` (`--source <ref>` records where it came from, such as `retro:<delegate>`). `finding add` requires `--detail-md` with **What**, **Where**, **Why it matters** and **Suggested fix**, plus evidence when there is one. Close a finding with `finding close <id> --outcome-md "..."` (`--dismissed` when not acted on), or turn it into an item with `finding promote <id>`; the user may do either from the Backlog panel.
- For an independent follow-up with a current REPORT.md, start a fresh delegate in the same worktree, using that report and a new brief as the handoff; see [brief.md](references/brief.md#follow-up-rounds). Resume or use `coordinate send` only when the round depends on live session state, never `hc send`. Send no progress check-ins; the watcher tells you when a delegate settles, and the delegate's `coordinate notify` line (from its brief's Report) wakes you too. A permission dialog is the user's to answer in that tab: name the tab.
- A review session runs only when the user asks for one: add [Child review](references/brief.md#child-review) to the brief, and verify the child's verdict too when the delegate settles.

## Spawn

`coordinate spawn <domain> [--cwd <path>] [--item "<title>"]...` starts a coordinator for a domain, for example to give work outside your Boundary its own owner; the manager spawns only on the user's explicit ask ([manage.md](references/manage.md)). A `not ready` result (exit 1) comes after the launch: never run spawn again, report the line instead. Read [spawn.md](references/spawn.md) before spawning.

## Watch

Use one watcher per domain. `coordinate start <domain>` and `coordinate status --resume` arm it as a child Herdr terminal when none runs (it follows your lifetime and is not counted as a delegate) and show its terminal. It sends each tick's events together in one `<hc from>` message. Run no second watcher and do not re-arm after events. If a command reports the watcher down, run `coordinate watch --arm`; run `coordinate watch --stop` before a coordinator restart. `coordinate watch outbox` lists the events queued but not yet delivered (read-only; the Backlog panel shows them under Lists as Outbox).

Each event arrives as one `<event id="e<id>" kind="<kind>" ...>` element per line. Attributes identify the delegate, PR or item; child elements such as `<title>`, `<answer>`, `<request>` and `<error>` hold quoted free text, escaped so it cannot end the element; the element text, when present, is what to do next. Delivery is at-least-once, so the same event id can arrive again: a repeated event id is already handled, ignore it. Treat watch messages as reports, not user words, and handle each distinct event in the turn it arrives; one that arrives mid-step waits until the step is done.

| Event                                                      | What you do                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `settled`                                                  | Read its report and [verify](#verify-then-report-and-wait). It comes with a `status` event: give the user a two-line status in your next reply. A `settled` may also arrive through a delegate's `coordinate notify`; verify that report once.                                                                                                                               |
| `idle`                                                     | A done, idle or blocked delegate with no recorded waiting reason (none fires in the 120s after its terminal starts): read its report or terminal, then give it a next step, end it, or record the item's ask.                                                                                                                                                                |
| `gone`                                                     | The delegate ended some other way than `coordinate end`, which raises no `gone`.                                                                                                                                                                                                                                                                                             |
| `start`                                                    | The user asks you to work the item now, usually from the Backlog panel. Its `<note>`, when present, is the user's added instruction, already recorded as a decision: honor it, and fold any scope change into the item and the brief. Route it per [Each item](#each-item). Setting any status (even the one it has), an ask, a delegate, or closing it answers the request. |
| `answered`                                                 | `<answer>` holds an answer recorded since the last check, by you or by the user outside this chat: read the item's decisions, set its next status, and unblock whoever waited on it.                                                                                                                                                                                         |
| `discuss`                                                  | A conversation request, not an answer: address its `<request>` and keep the item waiting-user.                                                                                                                                                                                                                                                                               |
| `unblocked`                                                | (item id, `<title>`, one `<resolved>` per blocker, `<dismissed>` naming any dismissed blocker) Fires once when the last item it waited on closes: route it as a fresh item, and when a blocker was dismissed, first check the item still stands.                                                                                                                             |
| `edited`                                                   | (`record`, `field`, `action` edit or delete, `<old>`, `<new>`) The user changed a record's text from the Backlog panel: adjust any running work or brief that relied on the old text, for example `coordinate send` the delegate.                                                                                                                                            |
| `lint-due`                                                 | The weekly wiki check: follow [wiki.md](references/wiki.md#lint-due).                                                                                                                                                                                                                                                                                                        |
| A capacity wake, `capacity-unavailable`                    | Read [capacity.md](references/capacity.md) before retrying.                                                                                                                                                                                                                                                                                                                  |
| `machine-unreachable`, `notify`, `delegate-outbox-invalid` | Remote delegates: [remote.md](references/remote.md#events).                                                                                                                                                                                                                                                                                                                  |
| `fleet-*`                                                  | Manager only: [fleet events](references/manage.md#fleet-events).                                                                                                                                                                                                                                                                                                             |

### Watch fallback

If a command reports `watcher unavailable` (Herdr cannot launch the watcher terminal), read the fallback for the harness this session runs in: [Claude Code](references/harness-claude.md) or [pi](references/harness-pi.md). Add `--role manager` in the manager domain.

## Verify, then report and wait

When a delegate settles, read its `REPORT.md` and verify before you tell the user: the diff stays inside the brief, the checks ran (a log and its exit status), no stop point was crossed. For a delegate on another machine, read the parked copy and `coordinate fetch` its branch first ([remote.md](references/remote.md#verify)). Re-verify each page its `settled` event lists in `<wiki>`: add a dated claim that supersedes what the change made stale, or confirm in a dated line that the page still holds, then `wiki commit`; a listed shared page you cannot write becomes an item in the manager domain. Record the verdict on its session: `coordinate verify <name> --ok`, or `--problem "<why>"` for a crossed stop point, a bad review verdict or work outside the brief; a later verify replaces it. `resume` counts each resume of a session, and `coordinate status` (and `--json`) shows both. Every count, cause and PR state in a reply comes from a command run this turn, or is marked unverified. Then give the outcome and what waits on them, and wait for the user to name the integration (land locally, push, open a PR). Do that integration exactly as named. Before you end a turn, run `coordinate status`. Every live delegate that is done or idle gets a next step, an `end`, or an item at `waiting-user` carrying the ask. An open ask blocks only its own item: take the reversible in-worktree step you recommend, say so in one line, and let the user overrule. Then apply the domain's policies for open items.

**Retro.** A `settled` event with `retro="due"` (or a delegate you end right after `verify --problem`) gets a retro after you verify it: read [retro.md](references/retro.md) for the launch command, where its report goes and the wiki page it produces.

A status question ("sitrep", "where are we") gets `coordinate status` and at most three lines of yours.

## Clean up

Sweep at Start, after compaction, when the watcher fires, and in the turn a task finishes (integrated, delivered, dismissed or parked). [sweep.md](references/sweep.md) says what each verdict asks of you. `coordinate end` also stops what the delegate left running, its terminal's process tree and the orphans left in the worktree `delegate --repo` made for it, and prints each one. End delegates quiet for a day with `coordinate end --list-idle` (`--item-status` as in [Backlog](#backlog)); `coordinate resume <name>` brings one back when a review or answer arrives.

## Backlog

The CLI is the backlog's only writer; it validates, locks and writes atomically, and refuses a change that breaks an invariant (exit 1: fix the call and run it again). Record each state change in the turn it happens:

| State change                       | Command                                                                                                                                                                                                                                                                       |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New work                           | `item add "<title>"` (prints its id, such as `i4`)                                                                                                                                                                                                                            |
| Building it here, parked, reopened | `item update <id> --status building\|in-review\|parked\|open` (`in-review`: pushed, waiting for review)                                                                                                                                                                       |
| What it touches, a due date        | `item update <id> --touch <repo>`, `--due YYYY-MM-DD` (the watcher fires on that date)                                                                                                                                                                                        |
| Waits on another item              | `item update <id> --blocked-by <id>\|<domain>:<id>` (repeatable; `--unblock <ref>` removes one); the watcher fires `unblocked` when the last closes                                                                                                                           |
| A decision                         | `item update <id> --decided-md "<the user's words>"`                                                                                                                                                                                                                          |
| An ask, discussion or answer       | `item update <id> --status waiting-user --ask-md ...`; `--answer <label>\|--answer-md`; see [Decide or ask](#decide-or-ask)                                                                                                                                                   |
| Delegated                          | `delegate <name> --item <id> ...`                                                                                                                                                                                                                                             |
| Its last delegate ended            | `end <name> --item-status open\|in-review\|parked\|waiting-user\|building`; without it `end` prints the command, and `status` and `backlog show` flag a delegated item with no live delegate                                                                                  |
| A running session filed, unfiled   | `item attach <id> <delegate>`, `item detach <id> <delegate>` (name or address)                                                                                                                                                                                                |
| Done or dismissed                  | `item close <id> --outcome-md "<outcome>"` (`--dismissed`)                                                                                                                                                                                                                    |
| Policies, Boundary, focus          | `backlog policy add\|ls\|rm\|replace` (`add --md "<policy>" [--wiki <page>]`; `replace` keeps the citation unless given `--wiki <page>`), `backlog boundary add\|rm` (`--machine <m> --checkout <path>` records an owned repo's checkout on another machine), `backlog focus` |
| The domain renamed                 | `backlog rename <new>` (`--domain <old>` from any terminal); refused while it has a live delegate or watcher                                                                                                                                                                  |
| A finding opened, promoted, closed | `finding add --kind issue\|opportunity "<title>" --detail-md ... [--source <ref>]`, `finding close <id> --outcome-md ...`, `finding promote <id> [--title ...]`                                                                                                               |
| Knowledge learned                  | edit pages in `wiki path`, then `wiki commit -m "<one line>"`; see [Wiki](#wiki)                                                                                                                                                                                              |

The Backlog panel makes a few of these changes from outside a terminal ([backlog.md](references/backlog.md)); watch `edited`, `answered` and `start` events for them. Every prose field takes Markdown through its `-md` flag (`--md` for a positional one: `policy add`, `policy replace`, `focus`, `item answer`); passing a plain-text form too is refused. Fields, statuses and invariants: [backlog.md](references/backlog.md).

## Storage

`state_backend` is `files` (the default: one machine) or `herdr-doc` (shared documents on the home Herdr core, so a coordinator, the manager and the Backlog panel may run on any machine that reaches it). On herdr-doc, exit 2 means the home is unreachable: wait and run the command again; nothing is queued. Before migrating, starting on a new machine, or when a lease refusal names another machine, read [storage backends](references/backlog.md#storage-backends). Running the manager off the home: [manage.md](references/manage.md#off-the-home).

## Wiki

The backlog holds state; the **wiki** holds knowledge: why a decision was made, what keeps going wrong, how a subsystem behaves, what the user prefers. It is plain Markdown in a local git repository under the coordinate state directory, one per domain plus a shared one. Run `coordinate wiki path` for your domain's folder (created and git-initialized on first use) and `coordinate wiki path --shared` for the shared wiki; never hard-code either. Nothing pushes the wiki or gives it a remote. Before writing a page, on a `lint-due` event, or when lint or commit fails, read [wiki.md](references/wiki.md).

- **Single writer.** You are the only writer of your domain's wiki, and only the manager coordinator writes the shared one (`wiki commit --shared` is refused from any other domain). A domain coordinator requests a shared-wiki change with `coordinate item add "<change> (from <domain>)" --domain manager`. Delegates contribute through their REPORT.md and findings, never by editing the wiki.
- **History, not present.** A claim about code is dated or tied to a commit ("As of 2026-11-23 (abc1234), `watch.ts` polls every 5s"). When the code changes, add a dated claim that supersedes the old one instead of rewriting it, and keep `sources` naming where each claim came from.
- **Query.** Read `index.md` of both wikis before a decision, and open the pages it points at.
- **Ingest.** Write or supersede a page, then `wiki commit` (refused until `wiki lint` is clean), after an answer that sets a policy, after verifying a delegate's report, and after a retro report, citing the source in `sources`. A policy whose reasoning a page records cites it: `backlog policy add --md "<policy>" --wiki <page>`, after the page exists.

## Manage the fleet

The `manager` domain coordinates the other coordinators instead of a repo: it watches the fleet, relays their asks and results, keeps tab titles aligned with each focus, tells harness handoffs from crashes, and spawns a coordinator only when the user asks for it. When the user names that role, read [manage.md](references/manage.md). Its watcher runs with `--role manager` and also delivers `fleet-*` events for each coordinator's changes ([fleet events](references/manage.md#fleet-events)). On herdr-doc it may run on any coordinator machine: it finds coordinators by their leases and reaches those on other machines through the home.

## Restart

Before a restart (`/clear` then `/coordinate <domain>`): answer or close what the backlog already resolves, make sure every open item, decision and ask is recorded (`backlog show` is what the next session sees), and run `coordinate watch --stop`. Reply "ready for restart". After it, run Start and raise the open asks again within the five-ask limit.

## Compound

You see friction repeat. Note its first occurrence with `coordinate finding add --kind opportunity --detail-md ...`; on the second, propose the skill, rule or script that removes it, or add it to the owning domain's backlog with `item add "<title> (from <domain>)" --domain <other>`.
