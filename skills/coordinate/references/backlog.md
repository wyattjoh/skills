# Backlog

One JSON document per domain at `<state_dir>/backlogs/<domain>.json` (default `~/.local/state/coordinate`), beside the watcher's `watch/` and `ended/` folders (an ended record's `machine` is the Herdr machine name the delegate ran on; records written before that field have none), `wiki-lint/` (each domain's last passing `wiki lint --mark` date) and `sessions/`, which keeps each delegate session's verify verdict and resume count. The `coordinate` CLI is its only writer: each command reads the document, applies one change, validates the result and writes it under a lock with a temp file and rename. Change it only through `backlog`, `item` and `finding` commands; `coordinate backlog show` renders it as Markdown and `--json` prints the document. It is working memory, not docs: plans, specs and reports live where the user keeps docs.

`coordinate start` creates the document. When `<backlog_dir>/<domain>-backlog.md` (default `~/.config/coordinate/backlogs`) exists from before, `start` records its path as `legacy` and never parses it; `backlog show` prints that pointer. Text output hides closed items by default and reports their count under Done; use `backlog show --done` or `status --resume --done` to include them. `--json` output is unchanged.

## Document

| Field           | Holds                                                                                                                                    | Set with                                                              |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `schemaVersion` | Always `1`                                                                                                                               | `start`                                                               |
| `domain`        | The domain name                                                                                                                          | `start`, `backlog rename <new>`                                       |
| `focus`         | One line on what the domain is doing now, or null; `focusMarkdown` holds it as inline Markdown                                           | `backlog focus --md "<line>"`, `--clear`                              |
| `legacy`        | Path of the old Markdown backlog, reference only, or null                                                                                | `start`                                                               |
| `boundary`      | `owned` and `adjacent` absolute paths; only `owned` feeds status, watch, sweep; optional `checkouts` map (see below)                     | `backlog boundary add\|rm <path> [--adjacent]`, `--machine` (below)   |
| `policies`      | `{ id, markdown \| text, at, wiki? }[]`: reusable rules with stable short ids (`p1`, `p2`, ...); `wiki` names the page that explains one | `backlog policy add\|ls\|rm\|replace`                                 |
| `items`         | The work (below)                                                                                                                         | `item add`, `item update`, `item close`, `item attach`, `item detach` |
| `findings`      | Issues and opportunities noticed outside an item's scope (below)                                                                         | `finding add`, `finding close`, `finding promote`                     |
| `nextId`        | The next shared item/finding id number; items use `iN`, findings `fN`                                                                    | item and finding adds                                                 |
| `nextPolicyId`  | The next policy id number (`p1`, `p2`, ...); removals do not reuse ids                                                                   | policy adds                                                           |

**Policies**: `backlog policy add --md "<policy>" [--at YYYY-MM-DD] [--wiki <page>]` appends a policy and prints its id. `--wiki` cites the page that explains the rule, by its name in the domain wiki or the shared wiki (the domain's is checked first); it refuses (exit 1, nothing written, no wiki created) when neither wiki has that page. The citation is stored as `wiki` and printed after the text as `(wiki: [[<page>]])` by `policy add`, `policy ls`, `policy replace` and `backlog show`, and beside the policy in the Backlog panel, as a link to the page when the domain wiki has it; `backlog show --json` includes it. `policy ls` lists ids, dates and text; `policy rm <id>` removes one; `policy replace <id> --md "<policy>" [--at YYYY-MM-DD] [--wiki <page>]` updates its body and date while preserving its id, and its citation unless `--wiki` names another page, checked and refused as `add` does. IDs are not reused after removal. Dates default to today. Each command supports `--domain` and `--json`.

A document that has `standingYes` but no `policies` migrates in memory when read: entries become `p1`, `p2`, ... in their existing order, preserving their text and date. Items without `answered` migrate in memory to `answered: []`; asks without `discuss` migrate to `discuss: null`, including asks in `answered` history. Read-only commands leave the source file untouched; its next successful write stores the `policies` field and no `standingYes` field, and stores `answered` and `discuss` for each item and ask. The panel uses the same validator and accepts both shapes.

## Markdown fields

Each prose field has an optional Markdown sibling, and new writes use it; the plain-text field and its flag are deprecated and stay readable for existing records. A record holds one or the other: the CLI refuses a text flag beside its `-md` flag, and the validator rejects a record holding both. With the sibling, a nullable text field is null and a required one (`decided[].text`, `policies[].text`, `ask.question`, `answered[].answer`) is absent; `discuss.note` is empty.

| Field                                | Markdown sibling            | Flag                                                           | Kind   |
| ------------------------------------ | --------------------------- | -------------------------------------------------------------- | ------ |
| `decided[].text`                     | `decided[].markdown`        | `--decided-md`                                                 | block  |
| `policies[].text`                    | `policies[].markdown`       | `policy add --md`, `policy replace --md`                       | block  |
| `ask.question`                       | `ask.questionMarkdown`      | `--ask-md`                                                     | inline |
| `ask.context`                        | `ask.contextMarkdown`       | `--context-md`                                                 | block  |
| `ask.optionDetails`                  | `ask.optionDetailsMarkdown` | `--option-md "<label> :: <detail>"` (label plain)              | block  |
| `ask.recReason`                      | `ask.recReasonMarkdown`     | `--why-md`                                                     | block  |
| `ask.discuss.note`                   | `ask.discuss.noteMarkdown`  | `--note-md` with a Discuss answer                              | block  |
| `answered[].answer` (free text only) | `answered[].answerMarkdown` | `--answer-md`, `item answer --md`                              | inline |
| `answered[].note`                    | `answered[].noteMarkdown`   | `--note-md`                                                    | block  |
| `outcome` (items, findings)          | `outcomeMarkdown`           | `--outcome-md` on `item update`, `item close`, `finding close` | block  |
| `findings[].detail`                  | `findings[].detailMarkdown` | `finding add --detail-md`                                      | block  |
| `focus`                              | `focusMarkdown`             | `backlog focus --md`                                           | inline |

Inline Markdown is one line (code, bold, links); block Markdown may hold paragraphs, lists and code. Option labels, `rec`, titles, paths and ids stay plain. An option label and `Discuss` stay on `--answer`; `--option` and `--option-md` cannot be mixed in one ask; `--decided-md` entries follow any `--decided` ones. Answer and discussion events in `decided` stay `text` and embed the question and answer source. `backlog show` indents multi-line Markdown under its bullet; `status`, `--json` and watcher events show it raw. The Backlog panel renders the sibling as Markdown and the text field, plain, only when there is none.

Older installed CLIs and panels reject a record whose required text field is absent (Markdown only), so install the panel and the CLI together before writing Markdown.

## Items

| Field                              | Holds                                                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `title`                            | One line                                                                                                                                |
| `status`                           | One of the statuses below                                                                                                               |
| `touches`                          | Repos the item changes (`--touch`, `--untouch`)                                                                                         |
| `decided`                          | `{ markdown \| text, at }`, dated user input or an ask event (`--decided-md`; answer and discussion requests append here)               |
| `ask`                              | `{ question, context, options, rec, recReason, discuss }` or null (`--ask-md`, `--context-md`, `--option-md`, `--rec`, `--why-md`)      |
| `ask.optionDetails`                | Optional strings aligned with `ask.options`; omitted when no option has a detail                                                        |
| `ask.discuss`                      | `{ note, at }` or null; a pending request to discuss before deciding, with an optional one-line note and request date                   |
| `startRequested`                   | `{ at }` while the user's start request (`item start`) is pending; absent otherwise                                                     |
| `edits` (document)                 | The user's edits from outside a terminal not yet delivered, `{ id, record, field, old, new, at }`; absent when none (with `nextEditId`) |
| `answered`                         | Completed asks, each preserving the question, context, options, recommendation, answer, and `answeredAt` date; `discuss` is null        |
| `due`                              | `YYYY-MM-DD` or null (`--due`, `--no-due`)                                                                                              |
| `delegates`                        | `{ name, session, branch, worktree, brief, report }`, recorded by `delegate --item` or `item attach`; removed by `item detach`          |
| `createdAt`, `closedAt`, `outcome` | When it was added and closed, and the outcome (`outcomeMarkdown` when written as Markdown)                                              |

Use `--option-md "<label> :: <detail>"` to store a detail; parsing splits at the first delimiter and the detail is optional.

| Status         | Means                                                              |
| -------------- | ------------------------------------------------------------------ |
| `open`         | Recorded, not started                                              |
| `building`     | You are building it in this session                                |
| `delegated`    | A delegate works on it                                             |
| `in-review`    | Pushed and waiting for review; `item close` it when review passes  |
| `waiting-user` | It waits on the user: an ask, or the integration they have to name |
| `parked`       | Set aside on purpose                                               |
| `done`         | Finished, with an outcome                                          |
| `dismissed`    | Dropped, with an outcome                                           |

The CLI refuses any change that would break these:

- A `delegated` item has at least one delegate; `delegate --item` and `item attach` add one and set the status, and `item detach` sets the item back to `open` when it removes the last. Ending the last live delegate leaves the item `delegated`; `end --item-status` sets its next status, and `status` and `backlog show` flag it (`[delegated, none live]`) until then.
- One session is filed under one item: attaching a session any item already names, open or closed, is refused with that item's id and the `item detach` command.
- A `waiting-user` item has an ask, or a decision naming the integration choice it waits on.
- An ask's `rec` is one of its `options`.
- `done` and `dismissed` items, and closed findings, have an `outcome` and a `closedAt`.
- Item, finding and policy ids are unique.

**Due dates**: the watcher fires once per item id and date, for items that are not closed. Editing the title does not fire it again.

**Answers, discussions and Boundary edits**: `coordinate item answer <id> <answer> [--note-md "<note>"] --domain <d>` (or `--md "<free text>"` in place of `<answer>`) records the same answer and optional note as `item update <id> --answer "<answer>" [--note-md "<note>"]`. `Discuss` or `Discuss: <note>` leaves the ask in place and the item `waiting-user`, stores `{ note, at }` in `ask.discuss` (an empty note when omitted), and appends `Discuss "<question>"` or `Discuss "<question>": <note>` to `decided`. It does not create an `answered` entry. A revised ask clears `ask.discuss`; a real answer moves the ask with `discuss: null`, the answer, and the `YYYY-MM-DD` answered date into `answered`, clears `ask`, and appends `Re "<question>": <answer>` to `decided`. The discussion decision is an event record, not a final choice. `backlog show` prints the pending marker and a `discuss <date>` event; `status` summarizes pending discussions, and the panel shows `In discussion` with the note. A later ask stays open alongside earlier answered asks, shown newest first. The watcher fires a `discuss` event (the item id, `<title>` and `<request>`) once for each discussion request and an `answered` event (the item id, `<title>` and `<answer>`) once for each real answer, whoever ran it. These are distinct events; a first arm, or a state file from before these events were tracked, seeds existing requests without firing them.

**Start requests**: `coordinate item start <id> --domain <d>` records the user's request that you start an item now as `startRequested: { at }` (the ISO time). It refuses a done, dismissed or delegated item, and while a request is pending it keeps the first one and exits 0. The request clears when `item update` sets a status (even the current one, as `--status building` does for an item you keep building yourself) or an ask, when a delegate is filed, and when the item closes; an answer that leaves the status alone keeps it. `backlog show` prints `start requested <at>, not yet acted on` and `status` lists it. The watcher fires a `start` event (the item id, `<title>`, `<requested>`) once per request. Unlike answers and discussions, a request pending on a first arm, or on a state file from before starts fired, fires rather than being seeded, because it is still waiting on you.

**Edits**: `coordinate item edit <id>` takes exactly one of `--title <line>`, `--outcome-md <md>` (a closed item) or `--decision <key>` with `--md <md>` or `--remove`; `coordinate finding edit <id>` takes one of `--title`, `--detail-md` or `--outcome-md` (a closed finding); `coordinate backlog boundary replace <path> <new> [--adjacent]` lists an existing path in place of one, keeping its place and an owned path's checkouts. Titles stay one plain line (they have no Markdown form); every other edit writes the Markdown sibling and clears the plain text. A decision's key is `<index>:<fingerprint>` (`decisionKey` in the store: its index in the stored `decided` list and an FNV-1a fingerprint of its date and text); a key that no longer matches is refused with the item's current keys. Answer (`Re "…"`) and discussion records stay as recorded, and a waiting-user item with no ask keeps its last decision. When a change comes from outside every terminal (`item edit`, `finding edit`, `policy replace`, `policy rm`, `backlog focus`, `boundary replace` and `boundary rm`), the CLI appends `{ id: c<n>, record, field, old, new, at }` to `edits` (`new` null for a delete; ids never reused, the newest 100 kept). The watcher queues an `edited` event per pending edit (`change`, `record`, `field`, `action`, `<old>`, `<new>`, `<at>`, each text cut at 2000 characters), then removes delivered edits from the document; a pending edit on a first arm is queued, not seeded. A coordinator's own edits record nothing.

Outside a Herdr terminal (`HC_TERMINAL_ID` unset), the Backlog panel may submit answers or discussion requests with `coordinate item answer <id> <answer> --domain <d>`, and edit paths with `coordinate backlog boundary add <path> [--adjacent] --domain <d>` or `coordinate backlog boundary rm <path> --domain <d>`, close an item with `coordinate item close <id> --outcome "<line>" [--dismissed] --domain <d>` (its Dismiss button), set an item's status to open, building, in-review or parked with `coordinate item update <id> --status <s> --domain <d>` and no other flag (the item detail's Change status), request a start with `coordinate item start <id> --domain <d>` (the item detail's Start), edit text with `item edit`, `finding edit`, `backlog policy replace|rm`, `backlog focus` and `backlog boundary replace` (see Edits), and approve or dismiss a finding with `coordinate finding promote <id> --domain <d>` or `coordinate finding close <id> --outcome "<line>" --dismissed --domain <d>` (the finding detail's Approve and Dismiss). These are the only backlog changes accepted from outside a terminal besides `backlog rename --domain` (below); `--domain` is required. Any terminal not labelled coordinator is still refused. Boundary add requires an existing path that is not already listed. Boundary rm removes the path from whichever Boundary list contains it and refuses a path in neither.

**Checkout map**: an owned path may record where its repo is checked out on other Herdr machines, in `boundary.checkouts` (owned path, then Herdr machine name, to the absolute path on that machine). The key is absent while no path has an entry. `coordinate backlog boundary add <owned path> --machine <m> --checkout <path on m>` adds an entry, and `coordinate backlog boundary rm <owned path> --machine <m>` removes one; both are accepted from outside a terminal with `--domain`, like the other Boundary edits. Add refuses a path that is not owned, a machine that `hc machine ls` does not list, this machine (`local`, its hostname or its Herdr name, since its checkout is the owned path itself), a checkout path that is not absolute, and a second, different checkout on the same machine (remove the old one first). The checkout path is stored as given (trailing slashes dropped) and never checked on this Mac's disk. Rm needs no registered machine, so an entry for a retired machine can still be removed. Removing an owned path drops its checkouts. `backlog show` lists each checkout under the Owned line as `  - <owned path> on <machine>: <checkout>`, `backlog show --json` prints the map, and the Backlog panel shows `<machine>: <checkout>` beside each owned path.

**Delegates**: the session id is the stable key, so a resumed delegate needs no update. A delegate started with `delegate --machine` also records `machine`, its Herdr machine name, and its worktree, brief and report paths are on that machine; the key is absent for this machine. `coordinate item attach <id> <delegate>` files a session already running, by name or terminal address: an unfiled delegate, or an agent the user started by hand. It records what `delegate --item` would have (the worktree and branch from the `fleet.worktree`/`fleet.branch` labels, else the Git checkout holding the terminal's folder, else null; brief and report under `<worktree>/.scratch/<name>/` when a `--cwd` start left a brief there, else under `<worktree>/.scratch/` when there is a worktree, else empty) and adds the labels `coordinate delegate` sets that the terminal lacks, never overwriting one. It refuses a coordinator, a terminal labelled for another domain, and one with no session id Herdr can see (no `fleet.session` label, no `--session-id` or `--resume` argument) unless `--session <id>` supplies it (Claude Code shows it in `/status`); a `--session` that differs from the one Herdr sees is refused. `coordinate item detach <id> <delegate>` takes a name, session id or address, works on closed items and ended delegates, and leaves the terminal's labels, so a live one shows as unfiled again. `coordinate status` adopts an unlabelled session the user started when an item's delegate names its session id. Ended delegates keep their record on the item; `coordinate status` lists them with their resume command.

## Findings

`{ kind, title, detail, path, from, source, createdAt, status, closedAt, outcome }`: `kind` is `issue` or `opportunity`, `from` the item it was noticed under, `source` where it came from when `finding add --source <ref>` gave one (such as `retro:<delegate>`; omitted otherwise, and `backlog show` prints it beside `from`), `createdAt` when `finding add` recorded it (findings added before the field existed have none), `status` `open`, `acted` or `dismissed`. `finding add` refuses a new finding without a detail (`--detail-md`, or the deprecated `--detail`) and names the shape ([SKILL.md](../SKILL.md)); it is a write rule, so findings stored without one stay valid. `coordinate wiki lint` flags an open finding whose `createdAt` is more than 14 days old. Delegates may run `coordinate finding add` (the domain comes from their terminal's label); every other change except `backlog rename --domain` is the coordinator's, and the CLI refuses it (exit 1) from any terminal not labelled `fleet.role=coordinator`, even with `--domain`. A coordinator's `--domain` may name another domain, which is how it routes an item there.

`coordinate finding promote <id> [--title "<title>"]` turns an open finding into an open item in the same domain, titled after the finding unless `--title` overrides it, and closes the finding as `acted` with the outcome `promoted to <item id>`, in one locked write. It refuses an unknown id and a finding already closed. `--json` prints `{ item, finding }`. The Backlog panel's finding detail runs it as Approve, and runs `finding close --dismissed` as Dismiss.

## Storage backends

`state_backend` in the config picks where the shared documents (backlogs, the harness policy, capacity queues and their claims, ended records) live. `files`, the default, is the layout above, written under lock directories. `herdr-doc` keeps them in the document store of one home Herdr core, named by `state_home` (its Herdr machine name; `local` or this host's name mean this core): `cs.b.<domain>`, `cs.q.<domain>`, `cs.k.<domain>` (claims), `cs.policy`, `cs.domains` (the index of domains, since Herdr cannot list documents) and `cs.ended.0` to `cs.ended.7` (ended records, sharded by session). Every write is a version-checked set with no lock: a write that loses a race re-runs the command on the fresh document, and after three lost races refuses (exit 1, run it again). A domain whose document name would pass Herdr's 32-character limit is refused (exit 1). A capacity claim in `cs.k.<domain>` is taken with the same version-checked set, so of two coordinators claiming one queued item at once exactly one wins. It records the owner's host, pid and an expiry 15 minutes out: on its own host a claim is held while its pid runs, and from another host until it expires, so a claim a dead coordinator left on another machine frees itself. Session state, the wiki lint clock, watcher snapshots and pids stay local files, and archives stay files on the home, in `home_state_dir` (the home's state dir, an absolute path) or, when that key is unset, at this machine's `state_dir` path relative to its HOME under the home user's HOME. From another machine, a backlog change appends its archive lines there through `hc exec` and `--done` reads them back with a remote file read; `backlog rename` must run on the home.

`coordinate state migrate --to herdr-doc` moves the shared documents from this machine's files to the home named by `state_home` (set it first; `state_backend` may still say `files`), and `--to files` moves them back. It copies every backlog, capacity queue, the harness policy and every ended record, checks each one landed, then retires the source: files move into `<state_dir>/files-backup-<UTC stamp>/` with their relative paths, each made read-only (mode 0444), and home documents are set to null. Moving back does not read that backup; it copies the home's current documents into the usual files, and the backup stays for manual recovery. The report lists every document with its old and new location (`(already there)` when the target already held the same value, as after an interrupted run) and ends with the `state_backend` line to set: migrate never edits the config, so switch it straight after. It refuses (exit 1) away from the home, because archives stay files there; while any domain has a watcher (its pid, or a labelled watcher terminal on any machine), a live delegate, or a queued launch retry holding a claim (claims are never copied); when a source document is unreadable; and when the target already holds a different document. Archives, session state, the wiki lint clock and watcher files stay where they are.

When the home is unreachable (`unavailable`, unknown to this core, or `hc` not answering), every read and write exits 2 naming the home; nothing is queued or read from a stale copy. Herdr cannot remove a document: deleting one leaves a tombstone (its name, a null value, a version) in the home core forever, which is a few bytes each, so the fixed set of names above stays small.

The watcher runs on its coordinator's machine and reads the backlog, policy and queue from the home every tick, as it reads the files on the files backend, so a change written from any machine fires the same events. On the home itself it also subscribes to the home core's document events, which only cut the wait for the next tick short; Herdr cannot subscribe to another machine's documents, so off the home it polls only. A tick that finds the home unreachable emits no backlog, policy or capacity events and leaves its snapshot alone; three in a row report `blind: state home <home> unreachable 3 times: ...`.

### Coordinator leases

Each backlog document carries a `lease`: `{ machine, address, expiry }`, the coordinator's Herdr machine (its core's own name), its terminal address as that core names it, and an ISO expiry. `coordinate start` takes it with a version-checked write for its terminal, and `coordinate spawn` takes it for the coordinator it launched, whose own start then takes it again; both refuse (exit 1) while another holder's lease is live, naming it as `<machine>/<address>`. The watcher renews its coordinator's lease every minute and never takes back one another coordinator took; a lease expires three minutes after its last renewal, so a crashed coordinator frees its domain within three minutes. Expiry compares clocks across machines, so keep them in sync. On both backends; `backlog show --json` includes it.

On `herdr-doc`, `coordinate start` first checks its own machine: bun on its PATH, a coordinate skill link (`~/.claude/skills/coordinate`, `~/.pi/agent/skills/coordinate` or `~/.agents/skills/coordinate`), and a Herdr route to the home (one document read). Anything missing is refused (exit 1) by name as that machine's own domain's setup to file there, never installed from here.

## Rename

`coordinate backlog rename <new>` renames this coordinator's domain, or `--domain <old>` from any terminal. Holding both domains' backlog locks, it writes `backlogs/<new>.json` (with `domain` set), `<new>.archive.jsonl` and `watch/<new>.json`, sets `domain` in each matching `ended/*.json` record, relabels the terminals carrying `fleet.domain=<old>` (a failed relabel is printed with its `hc label` command, not fatal), then removes the old files and a stale `watch/<old>.pid`. It refuses (exit 1) a new name `start` would refuse, a new name that already has a backlog or archive, an old domain with no backlog, a live delegate, and a live watcher. Text such as "(from <old>)" in other domains' items stays as written. It prints a warning when `keep_running` in the config names the old domain, and leaves a legacy Markdown backlog where the document's `legacy` field points.

A crash before the old backlog is removed leaves the old domain whole and a partial new one beside it (its ended records and labels possibly already renamed); delete `backlogs/<new>.json` and `<new>.archive.jsonl` and run it again with `--domain <old>`. A crash after leaves the rename done, with old archive or snapshot files to delete by hand.

## Retention

After each write, closed items and findings beyond the newest 50 move to `<state_dir>/backlogs/<domain>.archive.jsonl`, one record per line, so the history stays greppable. `backlog show --done` and `status --resume --done` list the archived items too, after the ones the document keeps.
