# Categories and verification rules

Every category is discovered by a cheap signal (usually a directory name) and then
confirmed by a separate proof that the directory is regenerable. Discovery alone
never authorizes deletion.

## Discovered by walking the roots

| Category       | Discovered by                      | Proof required            | Regenerated by             |
| -------------- | ---------------------------------- | ------------------------- | -------------------------- |
| `cargo`        | dir named `target`                 | contains `CACHEDIR.TAG`   | `cargo build`              |
| `xcode`        | dir named `DerivedData` or `build` | `git check-ignore` passes | Xcode build                |
| `node-modules` | dir named `node_modules`           | sibling `package.json`    | `npm`/`pnpm`/`bun install` |
| `swift`        | dir named `.build`                 | sibling `Package.swift`   | `swift build`              |

### Why these proofs

- **`CACHEDIR.TAG`** is written by cargo into every `target/` it creates. Directories
  named `target` are common in unrelated projects (a SQL migrations folder, a Java
  build output, a literal source directory), so the name alone proves nothing.
- **`git check-ignore`** is the strongest available signal for Xcode output. A repo
  that ignores a directory has declared it regenerable. `build/` in particular is a
  very common name for tracked source, so this check does real work.
- **A sibling manifest** distinguishes installed dependencies from a coincidentally
  named directory.

A candidate that fails its proof is reported under "Skipped" with the reason, and is
never deleted. That path is intentional: the scanner is designed to under-report
rather than over-delete.

## Exclusions that override the proofs

Two checks run before the per-category proof and veto it. Both exist because the
proofs above are necessary but not sufficient.

### Installed software

A globally installed CLI ships its dependencies in a `node_modules` beside a
`package.json`, which is exactly what the node-modules proof looks for. Nothing
rebuilds these, so deleting them silently uninstalls software.

Excluded prefixes, relative to home: `.ami`, `.asdf`, `.bun/install/global`,
`.cache/opencode`, `.claude/plugins/cache`, `.config/yarn/global`, `.deno`,
`.local/share/{fnm,mise,opencode,pnpm}`, `.npm-global`, `.npm/_npx`, `.nvm`, `.pi`,
`.plannotator`, `.volta`, `Applications`. Absolute: `/Applications`,
`/opt/homebrew/Cellar`, `/opt/homebrew/lib/node_modules`, `/usr/lib/node_modules`,
`/usr/local/lib/node_modules`.

Agent tooling is the easiest class to miss here. A Claude Code plugin, an MCP server,
or an agent runtime installs into a dot-directory in home and keeps its dependencies
in a `node_modules` beside a `package.json`, so it reads as a project. Deleting it
breaks the tool until it refetches. Conductor and worktree checkouts are the opposite
case and stay deletable: they are real project trees whose dependencies reinstall.

A real scan proposed deleting `~/.bun/install/global/node_modules`, which held 753
globally installed CLIs, along with the runtime dependencies of an installed editor.
Both passed the sibling-manifest proof. This exclusion is why they no longer do.

### Tool-managed caches

Package manager caches are reported with the vendor's cleanup command. The walker
also finds individual `node_modules` and `build` directories inside them, so without
this exclusion the same bytes would be deleted piecemeal _and_ recommended for
`bun pm cache rm`, double-counting the reclaim and desyncing the tool's index.

Excluded prefixes, relative to home: `.bun/install/cache`, `.cargo/registry`,
`.npm/_cacache`, `Library/Caches/Homebrew`, `Library/pnpm/store`.

### Adding to the lists

Both lists live in `scripts/classify.ts` as `HOME_INSTALL_PREFIXES`,
`SYSTEM_INSTALL_PREFIXES`, and `TOOL_CACHE_PREFIXES`. Matching is on segment
boundaries, so `.deno` does not match a project named `.deno-playground`.

## Known cache paths

Looked up directly rather than discovered. These are removed wholesale because the
owning tool treats them as a pure cache.

- `~/Library/Developer/Xcode/DerivedData`
- `~/Library/Developer/Xcode/{iOS,watchOS,tvOS,visionOS} DeviceSupport`
- `~/Library/Caches/ms-playwright`
- `~/Library/Caches/go-build` (`~/.cache/go-build` on Linux)

`DeviceSupport` regenerates the next time the matching device is connected to Xcode,
which takes a few minutes per device.

## Tool-managed caches

Reported with the vendor's own cleanup command instead of being deleted. Removing
these directories directly works but desyncs the tool's internal index, so the
vendor command is preferred.

| Tool     | Path                        | Command                   |
| -------- | --------------------------- | ------------------------- |
| homebrew | `~/Library/Caches/Homebrew` | `brew cleanup -s`         |
| pnpm     | `~/Library/pnpm/store`      | `pnpm store prune`        |
| cargo    | `~/.cargo/registry/cache`   | `cargo cache --autoclean` |
| bun      | `~/.bun/install/cache`      | `bun pm cache rm`         |
| npm      | `~/.npm/_cacache`           | `npm cache clean --force` |

`cargo cache` needs `cargo install cargo-cache` first.

## Deliberately out of scope

The scanner does not touch user data, even when it is large. Things like Messages
attachments, `~/Downloads`, Photos libraries, and CoreSimulator device images are
irreplaceable or expensive to rebuild, and deleting them is a decision for the user
rather than a tool. Report them if asked, but never remove them.

## Walk behavior

- A matched directory is not descended into, so artifacts nested inside artifacts
  are not double-counted.
- `.git`, `.hg`, `.svn`, `Library`, `Applications`, `.Trash`, and `*.app` bundles are
  pruned. `Library` is skipped during the walk because its caches are handled by the
  fixed-path lists above.
- Symlinked directories are skipped, so the walk cannot escape the root or loop.
- Depth defaults to 8 and is adjustable with `--max-depth`.
